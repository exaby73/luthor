---
title: How validators work
description: What a validator is, how chaining builds one, why they are immutable, and where field names in messages come from.
---

A validator is an immutable object that holds an ordered list of validations. Validating a value runs every validation in order and collects the messages of the ones that fail. This page explains the model behind the API so the reference pages make sense.

## Everything starts from `l`

`l` is a top-level getter that returns a fresh, empty `Validator`. The first method you call on it is usually a type, such as `string()`, `int()`, or `schema()`. A type adds one validation that checks the Dart type of the value, and for `string`, `int`, `double`, and `number` it returns a validator that also has the modifiers for that type.

```dart
l.string()  // has .email(), .min(), .regex(), and the other string modifiers
l.int()     // has .min() and .max()
l.list()    // no type-specific modifiers
```

`.required()`, `.custom()`, and `.customWithSchema()` return a plain `Validator`, so call the type-specific modifiers before them.

## Chaining adds validations

A modifier returns a new validator with one more validation appended. Order matters only for the order of messages. Every validation runs, so a failed input can produce several messages at once.

```dart
l.string().min(8).contains('@').validateValue('ab');
// errors: [value must be at least 8 characters long, value does not contain "@"]
```

## Validators are immutable

Chaining never changes the validator you chained from. A base validator can be shared and extended in several places without the extensions affecting each other. Define common validators once, at the top level or in a class, and reuse them across schemas.

```dart
final text = l.string();
final email = text.email();
final shortCode = text.length(6);

text.validateValue('hello').isValid;      // true
email.validateValue('hello').isValid;     // false
shortCode.validateValue('hello').isValid; // false
```

## Validations do not short-circuit

A string modifier on a non-string input reports the type failure, and the other validations still run and report too. When you show one message, show the first.

```dart
l.string().email().validateValue(42);
// errors: [value must be a string, value must be a valid email address]
```

## Field names in messages

Default messages start with the field name. Outside a schema there is none, so messages say `value`. Set one with `withName`. Inside a schema, the field key is the name.

```dart
l.string().email().validateValue('bad');
// value must be a valid email address

l.withName('email').string().email().validateValue('bad');
// email must be a valid email address

l.schema({'email': l.string().email()}).validateSchema({'email': 'bad'});
// {email: [email must be a valid email address]}
```

Call `withName` on `l`, before the type. Every generated schema starts with `l.withName('ModelName')`.

## Custom messages

Every type and modifier accepts `message` and `messageFn`. `message` is a fixed string. `messageFn` is a function called when the validation fails, for messages that depend on runtime state such as a locale. When both are given, `message` wins.

```dart
l.string().required(message: 'Email is required');
l.string().min(8, messageFn: () => tr('password.tooShort'));
```

The generator annotations take the same two parameters. `messageFn` has to be a top-level function or a static method so the generated code can refer to it.
